Technical architecture

Local admin, static public runtime.

Styxpress is built around a strict split: a local Go admin app for editing and publishing, and a static public website made of HTML, CSS, feeds, sitemaps, and assets.

Overview

The public site has no database, no hosted CMS process, and no dynamic request path. Styxpress renders content locally into static files, then deploys those files to a conventional web server such as Caddy or Nginx.

The admin runtime is a local Go binary. It starts an HTTP server bound to loopback by default, serves the embedded Vue admin UI, creates a temporary API session token, and prints the local URL needed to open the admin interface.

The public runtime is only static files. After rendering, the public directory contains pages, feeds, sitemaps, CSS, post assets, and cover images. The public server does not run Styxpress code and does not need access to the admin session, local API, source Markdown, or configuration files.

Startup And Admin Session Flow

The admin app is started manually from the command line. By default, it binds to a loopback address using an available local port, generates an API session token, and prints the local admin URL. The embedded UI uses that token to call the local admin API.

Terminal ./styxpress-admin [-addr 127.0.0.1:8080] [-config path]

The admin server is local-first. The generated public site does not include this API or session token.

Content-To-Public Rendering Pipeline

Content files are the source of truth. Styxpress reads the content directory, renders published posts with Goldmark, escapes raw HTML in Markdown, and writes a static public directory. Drafts are excluded from the public output, and local draft output is removed during a full site render.

content/
  • site.toml
  • featured.txt
  • posts/{slug}/source.md
  • metadata and assets
Renderer
  • Goldmark Markdown
  • raw HTML escaped
  • published posts only
  • siteBaseUrl applied
public/
  • index.html
  • posts/{slug}/index.html
  • feed.xml
  • sitemap.xml
  • assets/styxpress.css
Static host
  • Caddy or Nginx
  • no database
  • no dynamic public server

Rendering is eager and local: the public server only serves the generated files.

Publishing Modes

Publishing always uploads the rendered public files over SFTP. In local content mode, only the public output is deployed. In server-backed content mode, Styxpress can also upload the content directory so the remote server has a copy of the source content.

Mode A: Local content Local contentDir remains the source of truth.
Local publicDir Generated static output.
Remote public directory SFTP upload target served by the web server.
Mode B: Server-backed content Local contentDir is still rendered locally.
Remote content directory Optional source-content copy uploaded by SFTP.
Remote public directory Always receives rendered public files.

SFTP publishing is file-based. SCP is not part of the current publishing model.

Remote Verification

After publishing, Styxpress can compare local public files with remote public files. Verification uses file size and SHA-256 content hashes. The result is a file-by-file status model that shows whether the remote public directory matches the local render output.

Local public file
  • relative path
  • size
  • SHA-256
Remote public file
  • same relative path
  • size
  • SHA-256
Verification status
  • published
  • changes pending
  • not on remote
  • still on remote
  • unknown

Verification checks the deployed static files. It does not execute the public site and does not verify behavior on a dynamic server.

Published

The local file and remote file match.

Changes pending

Remote exists but size or SHA-256 differs.

Not on remote

The generated local file is missing remotely.

Still on remote

Draft output exists remotely after the post is no longer public locally.

Unknown

Verification did not run or a file could not be checked.

Filesystem Contracts

Styxpress uses plain files as its durable contract. The content directory is the authoring source. The public directory is generated output.

Default admin config

~/.config/styxpress/
  active-site.txt
  sites/
    default.toml
    field-notes.toml

When -config is used, Styxpress runs from that explicit file instead of the default multi-site store.

Explicit config mode

./styxpress-admin -config path/to/site.toml

Use this when a specific config file should define the site for this admin session.

Content source

content/
  site.toml
  featured.txt
  posts/
    {slug}/
      source.md
      title.txt
      description.txt
      published_at.txt
      updated_at.txt
      remote_synced_at.txt
      cover.*
      assets/

Public output

public/
  index.html
  feed.xml
  sitemap.xml
  assets/
    styxpress.css
  posts/
    {slug}/
      index.html
      cover.*
      assets/
  • Only published posts are rendered into public output.
  • Draft posts are excluded.
  • Draft output already present locally is removed during a full site render.
  • Markdown is rendered with Goldmark.
  • Raw HTML inside Markdown is escaped.
  • siteBaseUrl generates absolute feed, sitemap, canonical, and Open Graph URLs.

Admin API And Runtime Behavior

The Styxpress API belongs to the local admin runtime, not the public website. It is used by the embedded admin UI for local editing, rendering, publishing, and verification workflows. 

./styxpress-admin [-addr 127.0.0.1:8080] [-config path]

By default, the admin server binds to 127.0.0.1:0, which asks the operating system for an available local port. On startup, Styxpress prints the local URL and an API session token. The embedded UI receives the token and uses it for admin API requests.

No public Styxpress API.

The generated public site has no Styxpress API. Once deployed, production traffic is served as static files by the configured web server.

Security Model

Styxpress reduces the public attack surface by keeping the admin app local and publishing only static files. The production server does not need a database, a CMS process, or a writable application backend to serve readers.

The admin session token is created for the local admin runtime. It is not part of the rendered website and should not be deployed with public files. Markdown rendering escapes raw HTML, which keeps authored Markdown from becoming arbitrary raw HTML in generated public pages.

Host-key verification limit.

Strict host-key verification is not currently implemented. Do not treat SFTP publishing as hardened against all man-in-the-middle risks.

Current Limits

Styxpress is intentionally small in its current form. It does not currently provide:

  • Hosted CMS hosting.
  • A dynamic public server.
  • A database-backed public runtime.
  • Comments.
  • Analytics.
  • Public search.
  • Multi-user editing.
  • Scheduled publishing.
  • Rollback.
  • SCP publishing.
  • Arbitrary raw HTML in Markdown.
  • Strict host-key verification.
